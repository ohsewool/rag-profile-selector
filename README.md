# RAG Profile Selector — 인용이 어디를 가리키는지 측정한다

검색 평가는 보통 "맞는 청크를 가져왔는가"에서 멈춘다. 독자가 실제로 묻는 것은 다르다: **이 인용은 문서의 어디를 가리키며, 그 위치가 맞는가.**

```bash
python3 -m pytest tests/ -q                    # 150 tests
python3 experiments/citation_quality.py        # 프로파일 × 인용 품질 실험
```

## 왜 grounding 계층인가

식별자 단위 precision/recall이 못 보는 실패가 셋 있다.

| 실패 | 검색 지표에서 보이는 모습 | 독자가 겪는 일 |
|---|---|---|
| **ungrounded** | 평범한 오답 하나 | 아무 데도 닿지 않는 인용 |
| **misplaced** | 정답 (precision 1.0) | 답은 맞는데 포인터가 틀림 |
| **coarse** | 정답 | 구역이 있는데 페이지 단위로만 인용 |

`tests/test_grounding.py::TestComplementarityWithRetrievalMetrics`가 이 논지를 직접 보인다 — 검색 점수가 **완전히 동일한** 두 실행이 인용 정확도에서는 1.0과 0.0으로 갈린다.

## 실험 결과 (합성 코퍼스)

| 프로파일 | recall | top-1 인용 정확 |
|---|---|---|
| bm25-k4 | 1.0 | 0.75 |
| dense-k4 | 1.0 | 0.75 |
| hybrid-rrf-k4 | 1.0 | **1.0** |
| hybrid-rrf-k8 | 1.0 | **1.0** |

네 프로파일의 검색 recall이 전부 같은데 인용 정확도는 갈린다. **recall만 보고 프로파일을 고르는 선택기는 이 축에서 눈을 감고 고르는 셈**이다. hybrid 융합은 단일 검색기보다 인용도 나쁘지 않았다.

측정 함정 하나를 기록해둔다: 반환된 인용 전체를 평균하면 grounding 실패가 분모에서 빠져 **점수를 오히려 올린다**. 그래서 top-1 지표를 병기하고 리포트에도 캐비앳을 출력한다.

코퍼스는 합성이며 그렇게 명시한다. 이 숫자는 실제 문서에 대한 주장이 아니라 **측정 방식에 대한 주장**이다.

## 문서 모델과의 관계

`document-intelligence`는 별도 저장소로 두고 import 경계로만 의존한다(`docs/ADR-001-citation-grounding.md`에 근거). 좌표 검증은 여전히 그쪽 책임이고, `to_evidence_citation()`이 결과를 그 모델의 어휘로 되돌려준다. 문서 모델이 없으면 grounding 테스트만 skip된다.

## 선택기가 볼 수 있는 것

프로파일을 고르는 일은 검색이 실행되기 **전에** 알 수 있는 것만 보고 해야 한다 — 질의 자체, 그리고 각 검색기를 싸게 찔러본 결과. 정답 라벨이나 선택된 프로파일의 성적은 볼 수 없다. 그건 답이고, 답으로 만든 특징은 평가에서만 동작하는 선택기를 만든다.

이 규칙은 문서가 아니라 구조로 강제한다. `extract(query, probes, k)` 외에 라벨이 들어올 매개변수가 없고, `assert_no_leakage()`가 답에서 파생된 이름(gold·label·answer·quality·regret·outcome)을 거부한다.

측정 주의사항 하나도 코드에 반영했다: BM25 점수와 코사인 유사도는 **단위가 다르다**. 그래서 검색기 간 특징은 전부 순위 기반이고, 점수는 같은 검색기 안에서 비율로만 쓴다(40 대 20과 0.4 대 0.2가 같은 상황을 뜻하도록).

## 선택이 값어치가 있는지 먼저 재는 법

이 프로젝트의 질문은 "질의마다 프로파일을 고르는 것이 하나로 고정하는 것보다 나은가"다. 그래서 비교 상대가 코드에 함께 있다.

| 기준선 | 무엇인가 |
|---|---|
| fixed | 항상 같은 프로파일. 대부분의 시스템이 실제로 하는 것이자, 학습된 선택기가 넘어야 존재 이유가 생기는 선 |
| rule | 명시된 휴리스틱. 싸고 들여다볼 수 있으며, 의외로 이기기 어렵다 |
| oracle | 항상 사후에 최선이던 것. 답을 읽으므로 달성 불가 — **상한을 재는 용도** |

`headroom()`은 아무것도 만들기 전에 답을 준다: 최선의 고정 프로파일과 오라클의 격차. 이게 0에 가까우면 선택기가 아무리 좋아도 이 데이터에서는 도움이 안 되고, 그때 정직한 대응은 튜닝이 아니라 중단이다.

측정은 regret — 그 질의에서 최선이던 프로파일 대비 얼마를 포기했는가. 0은 검색이 좋았다는 뜻이 아니라 **그 질의에 대해 선택이 최적이었다**는 뜻이다.

아직 아무것도 학습하지 않는다. 학습된 선택은 도착하지 않은 코퍼스가 필요하고, 골격을 먼저 세워두면 유혹할 숫자가 생기기 전에 비교 방식이 확정된다.

## 데이터가 도착하기 전에 세워둔 관문

실험 계획이 요구하는 출처 기록 규약을 코드로 강제한다. 시간에 쫓기면 가장 먼저 건너뛰게 되는 부분이고, 그러면 반년 뒤에 어떤 코퍼스 버전이 그 숫자를 만들었는지 아무도 말할 수 없게 된다.

- 매니페스트가 불완전하면(출처·라이선스·버전·체크섬 중 하나라도 비면) **로드되지 않는다**
- 파일이 매니페스트의 체크섬과 다르면 로드되지 않는다 — "데이터는 바뀌었는데 버전 문자열은 그대로"인 조용한 실패를 잡는다
- 시드 없는 split은 재현할 수 없으므로 split으로 인정하지 않는다
- **test split은 프로토콜을 동결하기 전까지 봉인**된다. "테스트 결과가 설계에 영향을 주면 안 된다"는 규칙을 약속이 아니라 장치로 만든다

강제 우회 플래그는 없다. 없는 것이 요점이다.
